## 확정된 처리 방식
### ⑤ 리뷰 AI 요약 (하루 1회, 미리 계산)
1. Steam·다나와 리뷰 → raw → MongoDB `reviews` → Monstache → ES `reviews` (nori)
2. ES 집계로 게임별 추천/비추천 리뷰의 핵심 키워드 TOP 10 + 긍정 비율
3. **키워드와 비율만** AI에게 전송 (리뷰 원문은 보내지 않음) → 한두 줄 요약 (JSON)
4. `refined.review_summary` → MariaDB `review_summaries`

### ⑥ PC 사양 비교
- 게임 사양: Steam `appdetails`의 `pc_requirements` → 정제(HTML 정리) → `game_requirements`
- 사용자 사양: 마이페이지에서 CPU·GPU·RAM **선택 입력** → `user_specs`
- 비교: 게임 사양 + 사용자 사양을 AI에게 → `{"verdict": "rec_ok|min_ok|below_min", "reason": "..."}`
- 같은 게임 + 같은 사양 조합은 결과를 저장해 재사용 (Valkey `spec_check:{game_id}:{spec_hash}`)
- 사양 미입력 사용자 → 최소·권장 사양 표만 표시

### ④ 클리어 시간
HowLongToBeat가 아니라 **IGDB 자체 클리어 시간 데이터**(`game_time_to_beats`)를 쓴다.

## AI 사용 원칙
| | ⑤ 리뷰 요약 | ⑥ 사양 비교 |
|---|---|---|
| 호출 시점 | 하루 1회 배치 | 처음 볼 때 1회, 이후 저장 결과 |
| 보내는 것 | ES 키워드 20개 안팎 + 긍정 비율 | 최소·권장 사양 + 사용자 CPU·GPU·RAM |
| 받는 형식 | 요약 + 장점·단점 키워드 (JSON) | 판정 + 이유 한 줄 (JSON) |
| 실패 시 | 비율·키워드만 표시 | 사양 표만 표시 |

- 화면에 "AI 요약", "AI 판정" 표시. 키는 `.env`의 `GEMINI_API_KEY`. 무료 한도 확인 후 요약 게임 수 조절.

## 기술·발표 과제 8개
1. 3-Tier (Proxy → FE 2 → BE 2 → DB) — 완료
2. API 30개 이상(47개: 구현 46 + 리뷰 검색 1개 명세만) + 기능·API 명세서
3. Monstache (MongoDB 게임·리뷰 → ES)
4. ES 벤치마크: 게임 검색(MariaDB vs ES), 리뷰 키워드 추출(MongoDB vs ES)
5. 부하 테스트 (Locust)
6. 기술 스택 설명 (파트별 1개, 용도 → 이득)
7. 일정 관리 · 회고
8. 시나리오 · 시연 · 차트 시각화 (모니터링 시나리오 2~3개 포함)
