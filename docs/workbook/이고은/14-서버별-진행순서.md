# 14. 서버별 진행 순서 (처음부터 끝까지)

내 파트(테이블 설계 + 정제 프로그램)를 **어느 서버에서, 어떤 순서로** 진행하는지 한 번에 따라갈 수 있게 모았습니다.
각 단계의 자세한 설명은 9~13번 문서를 보고, 이 문서는 **순서와 서버 이름, 확인 기준**만 적습니다.
서버에서 확인하지 못한 것은 `⚠ 미확인`으로 표시했습니다. 비밀번호·키 값은 적지 않습니다.

## 14-1. 전체 순서 한눈에
| 순서 | 어디서 | 하는 일 | 상세 문서 | 확인 기준 |
|---|---|---|---|---|
| 0 | 내 PC | 코드 받기, 가상환경, 시험, `--dry-run` | 12-8 | `pytest` 140개 통과 |
| 1 | mariadb-pr | `erd.sql`로 테이블 29개 + `stores` 기본값 | 9-2, 13 | 테이블 29개 |
| 2 | mariadb-re | 복제로 테이블이 생겼는지 (읽기만) | 9-4 | IO·SQL 모두 `Yes` |
| 3 | kafka1 | 토픽 만들기 (`create-topics.sh`, 한 번) | 14-5 | `refined.*` 토픽이 목록에 있음 |
| 4 | kafka1~3 | refiner 환경 준비, 대응표, 서비스 시작 | 10-2~10-4 | `is-active`가 `active`, 로그에 오류 없음 |
| 5 | kafka1 | Connect 설정 등록 (한 대에만) | 11-2 | 커넥터 `RUNNING` |
| 6 | mariadb-pr, mariadb-re | 단계별 데이터 확인 (읽기만) | 11-3 | 행이 쌓이고 복제 정상 |
| 7 | kafka1~3 | 코드를 고쳤을 때 반영, 필요하면 다시 처리 | 10-4, 14-8 | 같은 순서로 3대 모두 |

> <- **순서의 이유:** 테이블(1)이 먼저 있어야 Connect(5)가 적재할 수 있고, 토픽(3)이 있어야 refiner(4)가 읽고 쓸 수 있습니다.
> 컬럼을 바꾸는 변경은 항상 **DB `ALTER` → Connect 설정 → refiner 배포** 순서입니다(13-7).
> <- 명령 앞의 `[adminc@서버이름 ~]$`에서 **서버 이름을 먼저 확인**합니다. 모르면 `hostname`을 입력합니다. mariadb-re(Replica)에서는 `SELECT`·`SHOW`만 합니다.

## 14-2. [내 PC] 0단계: 코드 받기와 시험
```
# 레포를 받는다 (처음 한 번). 이미 있으면 이 줄은 건너뛴다
[내 PC]$ git clone https://github.com/jyk222000/game-nuri.git && cd game-nuri

# 작업을 시작하기 전에 항상 최신으로 맞춘다 (팀 규칙)
[내 PC]$ git pull --rebase origin main

# 가상환경을 만들고 켠다. Python 3.12 를 쓴다
[내 PC]$ python -m venv .venv && source .venv/bin/activate

# 공통 패키지(shared)를 개발 모드로, pipeline 의존성을 설치한다 (confluent-kafka, requests, rapidfuzz)
(.venv) [내 PC]$ pip install -e shared -r pipeline/requirements.txt

# 정제 규칙 시험을 돌린다. Kafka 도 DB 도 필요 없다
(.venv) [내 PC]$ python -m pytest pipeline/tests
```
> <- 성공 기준: `140 passed`. 규칙 파일을 고쳤다면 이 시험이 통과한 뒤에만 서버에 올립니다.
> <- 서버(kafka1~3)가 필요한 부분은 `main.py`의 Kafka 모드뿐입니다. 규칙은 모두 내 PC에서 시험됩니다.

## 14-3. [mariadb-pr] 1단계: 테이블 만들기
```
# 서버 이름 확인. 테이블은 Primary(쓰기 서버)에서만 만든다
[adminc@mariadb-pr ~]$ hostname

# 최신 스키마 파일을 받는다 (서버 레포의 git 에는 sudo 를 붙이지 않는다)
[adminc@mariadb-pr ~]$ cd /opt/game-nuri/repo && git pull

# 시간대가 UTC 이고 문자셋이 utf8mb4 인지 확인한다. 팀 규칙: 시간은 항상 UTC 로 저장
[adminc@mariadb-pr ~]$ sudo mariadb -e "SELECT @@hostname, @@time_zone, @@character_set_server;"

# 스키마를 적용한다. CREATE TABLE 29개가 만들어진다. 비밀번호는 입력창에서 직접 친다
# DB VM 안에서 gamenuri 계정으로 접속할 때는 localhost 가 아니라 자기 IP(10.0.2.101)를 쓴다
[adminc@mariadb-pr ~]$ mariadb -h 10.0.2.101 -u gamenuri -p < /opt/game-nuri/repo/docs/contracts/erd.sql

# stores 에 판매처 8곳을 넣는다. INSERT IGNORE 라 여러 번 실행해도 안전하다
[adminc@mariadb-pr ~]$ sudo mariadb gamenuri < /opt/game-nuri/repo/docs/contracts/erd_seed_stores_1123.sql

# 테이블이 29개인지 센다
[adminc@mariadb-pr ~]$ sudo mariadb gamenuri -e "SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='gamenuri';"
```
> <- **이미 테이블이 있는 서버**에서는 `erd.sql`을 다시 넣지 않고 바뀐 부분만 담은 `erd_alter_*.sql`을 씁니다(13-7). 파일 안의 실행 전 조건(예: 가격 테이블이 비어 있을 것)을 먼저 확인합니다.
> <- `DROP`, `TRUNCATE`는 실행하지 않습니다. 필요하면 팀장 확인을 받고 팀장이 실행합니다.
> <- ⚠ 미확인: 계정 분리(`gamenuri_connect`, `gamenuri_app`)는 발표 뒤로 미뤄져 있어(`infra/mariadb/README.md` 남은 일), 지금은 `gamenuri` 계정 하나로 Connect·Backend가 접속합니다.

## 14-4. [mariadb-re] 2단계: 복제 확인 (읽기만)
```
# 서버 이름 확인. 여기서는 SELECT·SHOW 만 입력한다 (Replica 에 쓰면 복제가 멈춘다)
[adminc@mariadb-re ~]$ hostname

# Primary 에서 만든 테이블이 복제로 생겼는지 본다
[adminc@mariadb-re ~]$ sudo mariadb gamenuri -e "SHOW TABLES;"

# 복제 상태. Slave_IO_Running, Slave_SQL_Running 이 모두 Yes, Seconds_Behind_Master 가 0 에 가까워야 한다
[adminc@mariadb-re ~]$ sudo mariadb -e "SHOW REPLICA STATUS\\G"
```
> <- 명령이 안 되면 `SHOW SLAVE STATUS\\G`로 입력합니다(MariaDB 버전에 따라 다름).

## 14-5. [kafka1] 3단계: 토픽 만들기 (남현식 파트, 한 번만)
```
# 서버 이름 확인. 토픽은 kafka1 에서 한 번만 만든다
[adminc@kafka1 ~]$ hostname

# 토픽을 만든다. 이미 있으면 건너뛴다(--if-not-exists). 파티션 3, 복제 3 이다
# raw.* 는 7일, refined.* 는 3일 보관. 정제가 만드는 토픽 14개(연결 토픽)도 같이 만든다
[adminc@kafka1 ~]$ bash /opt/game-nuri/repo/infra/kafka/create-topics.sh

# 목록에 raw.price, raw.console, raw.steam, raw.igdb, refined.prices, refined.games, refined.unmatched 등이 있는지 본다
[adminc@kafka1 ~]$ kafka-topics.sh --bootstrap-server kafka1:9092 --list
```
> <- **삭제 금지:** 토픽 삭제와 offset 초기화는 팀장 확인 후에만 합니다. 한 번 넣은 메시지는 지울 수 없고 Connect가 DB에 넣습니다.
> <- 시험 메시지는 시험용 토픽(`test.smoke`, 보관 1시간)에만 넣습니다. 실제 토픽에는 넣지 않습니다.

## 14-6. [kafka1~3] 4단계: refiner 켜기
세 대(kafka1, kafka2, kafka3)에서 **같은 순서로** 합니다. 같은 consumer group(`refiner`)이라 파티션을 나눠 맡습니다.
```
# 서버 이름 확인. 세 대 중 어느 서버인지 매번 확인한다
[adminc@kafka1 ~]$ hostname

# 최신 코드를 받는다 (git 에 sudo 를 붙이지 않는다. 붙이면 .git 이 root 소유가 되어 다음 pull 이 막힌다)
[adminc@kafka1 ~]$ cd /opt/game-nuri/repo && git pull

# 가상환경에 의존성을 설치한다 (처음 한 번, 또는 requirements 가 바뀌었을 때)
[adminc@kafka1 repo]$ .venv/bin/pip install -r pipeline/requirements.txt -e shared

# 환경 파일을 확인한다. 비밀번호는 없다. 아래 세 줄이 있어야 한다
#   KAFKA_BOOTSTRAP=kafka1:9092,kafka2:9092,kafka3:9092
#   ID_MAP_PATH=/opt/game-nuri/repo/pipeline/refiner/id_map.json
#   ID_MAP_STATE_PATH=/var/lib/game-nuri/refiner_id_map.json
# (가격 이력을 이어 가려면 PRICE_STATE_PATH=/var/lib/game-nuri/refiner_last_prices.json 도 둔다)
[adminc@kafka1 ~]$ sudo cat /etc/game-nuri/refiner.env

# 서비스를 켠다. 코드는 시작할 때 읽으므로 코드를 바꿨다면 restart 한다
[adminc@kafka1 ~]$ sudo systemctl restart refiner

# 켜졌는지 확인한다. active 가 나와야 한다
[adminc@kafka1 ~]$ sudo systemctl is-active refiner

# 로그를 본다. "refiner start: ..." 줄이 나오고 오류가 없어야 한다 (Ctrl+C 로 빠져나온다)
[adminc@kafka1 ~]$ sudo journalctl -u refiner -f
```
> <- 시작 로그에 "대응표가 비어 있다" 경고가 나오면 `id_map.json`이 비어 있는 것입니다. 그러면 가격·사양이 게임에 연결되지 않고 `unmatched`로 갑니다(10-2).
> <- 서비스 정의는 `infra/kafka/systemd/refiner.service`입니다(`User=refiner`, `Restart=on-failure`, 10초 뒤 재시작, 작업 폴더 `/opt/game-nuri/repo/pipeline`).
> <- ⚠ 미확인: ① `refiner.env.example` 파일이 레포에 없습니다(문서에는 언급됨). ② `/var/lib/game-nuri/` 폴더와 `refiner` 계정이 세 대 모두에 만들어져 있는지, 실제 Kafka 모드로 정상 처리되는지는 서버에서 확인하지 못했습니다(`pipeline/refiner/README.md`도 "Kafka 모드는 실제 Kafka에서 실행해 보지 못했다"고 적고 있음).

## 14-7. [kafka1] 5단계: Connect 설정 등록과 [mariadb-pr·re] 6단계: 데이터 확인
```
# 등록은 kafka1 한 대에서만 한다 (설정이 Kafka 내부 토픽에 저장되어 3대가 나눠 맡는다)
[adminc@kafka1 ~]$ cd /opt/game-nuri/repo/pipeline/connect && ./apply.sh jdbc-sink-prices-current jdbc-sink-price-history

# 상태가 RUNNING 인지 확인한다. FAILED 면 trace 에 원인이 나온다
[adminc@kafka1 connect]$ curl -s http://kafka1:8083/connectors/jdbc-sink-prices-current/status

# 저장된 행 수를 본다 (mariadb-pr, 읽기만)
[adminc@mariadb-pr ~]$ sudo mariadb gamenuri -e "SELECT COUNT(*) FROM games; SELECT COUNT(*) FROM prices_current; SELECT COUNT(*) FROM price_history;"

# 정제 실패가 얼마나 있는지 본다 (MongoDB unmatched 컬렉션에 쌓인다). 많을수록 ID 통합이 덜 된 것이다
[adminc@kafka1 ~]$ sudo journalctl -u refiner -n 50 --no-pager
```
> <- `.env`에 `KAFKA_CONNECT_URL`, `MARIADB_USER`, `MARIADB_PASSWORD`, `MONGO_URI` 등이 있어야 `apply.sh`가 동작합니다(값은 문서에 적지 않음, `chmod 600`, 커밋 금지).

## 14-8. 코드를 고친 뒤 다시 처리해야 할 때 (⚠ 팀장 확인 후)
정제 규칙을 고치면 **이미 처리한 메시지는 옛 규칙으로 정제된 채** 남습니다. 새 규칙으로 처음부터 다시 처리하려면 offset을 처음으로 되돌립니다.
```
# ⚠ 팀장 확인 후에만 실행한다. refiner 3대를 먼저 모두 멈춘다 (offset 초기화는 그룹이 멈춰 있어야 된다)
[adminc@kafka1 ~]$ sudo systemctl stop refiner     # kafka1, kafka2, kafka3 모두

# 먼저 --dry-run 으로 어디가 바뀌는지 본다 (--execute 를 빼면 실행되지 않고 결과만 보여 준다)
[adminc@kafka1 ~]$ kafka-consumer-groups.sh --bootstrap-server kafka1:9092 --group refiner --reset-offsets --to-earliest --all-topics --dry-run

# 사용자(팀장) 확인 뒤에 실제로 되돌린다
[adminc@kafka1 ~]$ kafka-consumer-groups.sh --bootstrap-server kafka1:9092 --group refiner --reset-offsets --to-earliest --all-topics --execute

# 다시 켠다 (세 대 모두)
[adminc@kafka1 ~]$ sudo systemctl start refiner
```
> <- ⚠ 되돌릴 수 없음: 다시 처리하면 `refined.*` 토픽에 결과가 다시 쌓이고 Connect가 DB를 다시 씁니다. `prices_current`는 upsert라 같은 키가 덮어써지지만, **`price_history`는 insert라 줄이 겹칩니다**(Backend가 조회 때 합칩니다).
> <- 같은 이유로 `PRICE_STATE_PATH` 파일(지난 가격 기억)을 지우지 않으면 "바뀐 것만 이력으로" 규칙 때문에 이력이 다시 쌓이지 않을 수 있습니다. 어떻게 할지는 팀장과 정합니다.

## 14-9. 자주 막히는 곳
| 증상 | 원인 | 해결 |
|---|---|---|
| Sink가 `FAILED`, 로그에 컬럼 없음 | 메시지 필드가 테이블 컬럼보다 많다 | `erd.sql`/`ALTER`를 먼저 맞춘다(DB → Connect → refiner 순서) |
| `1130 Host ... is not allowed` | 접속 이름이 IP로 해석되어 허용 대역과 다르다 | DB 서버에 `skip-name-resolve` (구축 기록 참고) |
| 가격이 전부 `unmatched` | 대응표(`id_map.json`)가 비어 있다 | 시작 대응표를 만든다(10-2) |
| `git pull`이 권한 오류 | `sudo git`을 한 적이 있다 | `.git` 소유자를 확인한다. 이후에는 `sudo` 없이 한다 |
| 명령이 다른 서버에서 실행됨 | MobaXterm 탭 혼동 | 항상 `hostname`부터. 같은 명령을 여러 대에 넣을 때는 MultiExec 대상을 먼저 확인 |
