# 1. 구상: 데이터가 흐르는 길과 설계 결정

## 1-1. 전체 흐름
```
수집기(collector) --raw.*--> Kafka --> [정제 프로그램 refiner] --refined.*--> Kafka
                                                                   |
                     Kafka Connect <--------------------------------+
                       |- refined.* -> MariaDB (테이블 29개)
                       `- raw.*     -> MongoDB -> Monstache -> Elasticsearch
```
- 수집기는 받은 원본을 **정제하지 않고** `raw.*` 토픽에 그대로 보냅니다.
- 정제는 **내가 만든 refiner**가 하고, DB 저장은 **Kafka Connect**가 합니다.
- Backend는 가격·게임 테이블에 쓰지 않습니다. 조회와 사용자·알림 데이터만 씁니다.


## 1-2. 설계 결정과 이유
| 결정 | 이유 |
|---|---|
| 정제는 Kafka 쪽 refiner, DB 적재는 Kafka Connect | Backend가 API만 맡도록 하려고 (강사 피드백). 단계가 나뉘어 설명하기 쉽다 |
| 기준 게임 ID = IGDB ID, 스토어별 ID는 `game_store_ids` | 스토어마다 게임 번호가 달라서 하나로 묶는 기준이 필요. (store, external_id)를 키로 해서 같은 번호가 게임 둘에 붙지 않게 한다 |
| 테이블 컬럼 이름 = 메시지 필드 이름 | JDBC Sink는 메시지 필드를 모두 컬럼에 넣는다. 컬럼이 없으면 적재가 멈춘다 |
| 시간은 UTC, 금액은 원화 정수 `price_krw` | 팀 규칙. 원래 통화는 `price_original`, `currency_original`에 따로 둔다 |
| 가격 키에 `platform`, `item_condition`(new/used) 추가 | 같은 게임의 PS4·PS5, 신품·중고가 서로 덮어쓰지 않게 하려고 |
| 장르·플랫폼을 별도 테이블로 분리 (1NF) | 쉼표로 이어 붙인 문자열은 검색·집계가 어렵다 |
| 정제 실패는 `refined.unmatched`에 기록 | 버리면 왜 빠졌는지 알 수 없다. 건수가 줄수록 ID 통합이 잘 된 것 |
| 같은 메시지를 두 번 처리해도 결과가 같게 | Kafka는 같은 메시지를 다시 줄 수 있어서 |
