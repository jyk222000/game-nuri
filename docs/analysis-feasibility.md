# 분석 8개 구현 가능성 점검 (수집 컬럼 기준)

> 기준일: 2026-11-21.
> **판단 기준: `docs/collector-test/column-mapping.md`의 컬럼 이름.** ERD는 아직 확정 전이라 `erd.sql` 초안은 쓰지 않았다.
> 확정된 전제: 게임 **1,000개**, 리뷰 수집 **상한은 이미 정해짐**(값과 방식은 이 문서에 없다. 아래 문제 2번에서 필요한 이유를 적었다).
> 일정 근거: Notion "서버정보"(수집기 타이머 11/24, 전체 흐름 검증 11/26, 발표 11/30).
> 분석 방향 원문: Notion "분석 방향" (#1~#8).
> **문서만 보고 판단했다.** DB에 실제 데이터가 들어온 뒤 분석을 돌려 확인한 것은 아니다.

## 한 줄 결론
- **컬럼 이름만 보면** 4개는 추가 없이 가능(✅ 1·2·4·5), **2개는 컬럼 추가가 필요(🔶 3·7)**, 1개는 정의가 더 필요(⚠️ 6), 1개는 일부 불가(❌ 8).
- **그러나 구현을 막는 가장 큰 문제는 컬럼이 아니라 "시간"이다.** 동접자·다나와 가격처럼 **새로 쌓이는 것밖에 없는 데이터**가 있고, 발표(11/30)까지 쌓이는 기간이 며칠뿐이다. 리뷰도 **수집 상한 방식에 따라 오래된 구간이 잘릴 수 있다.**
- **새로 쌓이는 데이터는 분석뿐 아니라 서비스 기능에도 영향을 준다.** 분석 8(화제성)·2(동접 부분)·1(콘솔), 기능 ② 콘솔 게임의 구매 타이밍·할인 예측, 콘솔의 가격 이력·역대 최저가(#11·#12), ⑦ 접속자 적은 게임 경고(#33), ⑨·⑩의 시연 데이터가 해당한다. 자세한 내용은 아래 "새로 쌓이는 데이터가 미치는 영향" 절.

## 데이터 시점: 과거를 가져올 수 있나, 새로 쌓이는 것뿐인가
| 데이터 | 과거 이력 | 비고 |
|---|---|---|
| ITAD 가격 이력 (`history/v2`) | ✅ 과거 전체 | 변동 시점 기록이라 일 단위 변환 필요 (문제 5) |
| Steam 리뷰 본문 | ✅ 작성 시각(`timestamp_created`)으로 과거 복원 | **상한 방식에 따라 잘림** (문제 2) |
| IGDB·Steam 정적 정보 (출시일, 제작사, 장르, 사양, 클리어 시간) | 현재 값만 | 변경 이력은 없지만 분석에는 충분 |
| 외부 평점, 업적 달성률, ITAD info `players` | 현재 값 하나 | 변화를 보려면 주기 수집이 필요 |
| Steam 리뷰 요약(긍정률) | 현재 값 | 리뷰 본문이 충분하면 시점별로 다시 계산 가능 |
| **동접자 (`player_counts`)** | ❌ **수집 시작일부터** | 소급 불가 (문제 1). 영향: 분석 8·2, 기능 ⑦ |
| **다나와 가격** | ❌ 이력 수집 불가, **스냅샷만** | 6시간 주기 (문제 1). 영향: 분석 1(콘솔), 기능 ②(콘솔)·#11·#12 |
| Steam 뉴스(업데이트 날짜) | ❓ 시험 전 | 과거가 얼마나 오는지 확인 필요 |
| 클릭스트림·API 사용 | ❌ 서비스 시작일부터 | 분석 8개의 대상은 아님. 영향: 기능 ⑨·⑩ 시연 |

### 발표까지 쌓이는 양 (계산)
수집이 시작된 지 N일일 때 게임 1개당 건수. 계획표(수집기 타이머 11/24, 전체 검증 11/26, 발표 11/30)를 가정한 값이다.

| 수집 기간 | 동접자 (1시간 주기) | 다나와 (6시간 주기) |
|---|---|---|
| 4일 (11/26~11/30) | 96건 | 16건 |
| 6일 (11/24~11/30) | 144건 | 24건 |

→ 동접자로 "화제성 추이"를 만들기에는 짧고, 다나와 스냅샷으로 "콘솔 할인 주기"를 예측하기에는 턱없이 적다. **동접자 수집은 시작이 늦어질수록 데이터가 그만큼 줄어든다.** 어떤 분석·기능에 어떻게 영향을 주는지는 바로 아래 절.

## 새로 쌓이는 데이터가 미치는 영향 (분석·서비스 기능별)
새로 쌓이는 데이터는 **동접자, 다나와 스냅샷, 클릭스트림·API 사용 로그** 세 가지다. ITAD 이력, Steam 리뷰, IGDB·Steam 정적 정보는 과거를 가져올 수 있어서 이 문제와 상관없다. 서비스 기능 번호(①~⑩)와 API 번호는 `docs/features.md`·`docs/contracts/api.md` 기준이다.

### 1) 데이터별로 어디에 쓰이고, 모자라면 무슨 일이 생기나
| 데이터 | 쓰이는 분석 | 쓰이는 서비스 기능·API | 모자랄 때 생기는 일 |
|---|---|---|---|
| **동접자** (`player_counts`) | 8(화제성 지수), 2(동접 지수) | ⑦ 동접자 기반 추천·경고: #32 `players/top`, #33 `players/low`, 게임 상세의 동접 표시 | **분석 8:** 현재 설계(`a08_buzz.py`)의 화제성 지수는 "직전 14일 중앙값 대비"라 4~6일치로는 **기준선을 만들 수 없다.** 급상승 원인 비율·반감기도 수집 기간에 일어난 사건 몇 건으로만 계산돼 믿을 수 없다. **분석 2:** "할인 시작 전후 30일" 비교는 수집 시작 전에 시작한 할인에는 동접 데이터가 없어서, **수집 기간 중에 시작한 할인만** 쓸 수 있다. **⑦:** #32 인기 게임은 현재 값으로 동작한다. #33 경고는 "적다"의 기준이 절대값·순위면 가능하지만 "평소보다 적다"면 평소 값이 없어 불가능하다. 동접 추이 그래프도 며칠치뿐이다. 요일 패턴은 7일 이상 있어야 보이고, 시간대 패턴은 하루치로도 볼 수 있다 |
| **다나와 스냅샷** (콘솔 가격, 6시간 주기) | 1(콘솔 판매처·월), 구매 타이밍 예측 | ① 가격 비교(콘솔), ② 구매 타이밍 #15·할인 예측 #16, #11 가격 이력, #12 역대 최저가, ③ 목표가 알림(콘솔) | **②:** 콘솔 게임은 할인 주기(수십 일)를 예측할 수 없다. PC 게임은 ITAD 이력이 있어 영향이 없다. **#11·#12:** 콘솔은 "역대 최저가"가 실제 역대가 아니라 **수집 시작 이후 최저가**가 되어 사용자가 오해할 수 있다. **분석 1:** 콘솔 행은 제외하고 PC만 분석한다. **①·③:** 현재가 기준이라 **영향 없음** (6시간 주기 수집으로 알림이 동작한다) |
| **클릭스트림·API 사용 로그** (서비스 시작 후) | 분석 8개의 대상 아님 | ⑨ 실시간 검색어 #34·#35, ⑩ API 사용 순위 #37 | 시연 때 트래픽이 없으면 순위가 비어 있다. ⑨는 명세에 "부족하면 더미"가 이미 있다. ⑩은 Locust 부하 테스트(과제 5)나 시연 중 호출로 채울 수 있다 |
| **현재 값만 있는 것** (외부 평점, 업적 달성률, ITAD `players`, Steam 리뷰 요약) | 3, 6(개인 기능 제안) | ⑤ 리뷰 요약 | 현재 값끼리 비교하는 분석이라 **영향 없음.** "시간에 따라 변하는 모습"을 보여 주는 기능을 새로 만들면 불가능하다 |

### 3) 대응 (화면·발표 표현)
- **8번:** "리뷰 증가율 + 할인 시점"으로 지표를 줄이거나, 수집 N일치 기반의 초기 결과·가설로 소개한다.
- **2번:** 동접 패널에 "수집 N일치"를 표시한다.
- **②:** 콘솔 게임은 "가격 데이터를 쌓는 중이에요"로 표시하고 예측을 내지 않는다.
- **#12 콘솔:** 라벨을 "수집 이후 최저가"로 한다.
- **⑦ 경고:** "적다"의 기준을 절대값(또는 순위)으로 정의한다 (팀 결정 필요).
- **⑨·⑩:** 시연 전에 더미·부하 테스트로 채운다.
- **공통:** 동접자 수집을 가능한 한 먼저 가동한다. 시작일이 곧 데이터 양이다.

## 컬럼 추가 요청
`column-mapping.md`에는 없지만 수집 시험에서 이미 받고 있는 필드(플랫폼별 출시일, 평론 점수 등)는 **`docs/column-additions-request.md`** 에 따로 정리했다.

## 정해야 할 것
1. **리뷰 상한의 값과 방식** (문제 2) — 분석 2·3·4·5의 표본과 과거 구간을 정한다.
2. **동접자 수집 시작일** (문제 1) — 앞당길수록 데이터가 는다. 분석 8·2와 기능 ⑦에 영향.
3. **AAA/인디 기준** (분석 1·3). 가격, 제작사, 태그, `rating_count` 중 무엇으로 나눌지.
4. **성능 키워드·불만 유형 사전** (분석 4·5). 어떤 단어를 어떤 유형으로 셀지. 분석 5번은 **ES에서 성능 키워드별 언급 수(최근 6개월)를 집계**해서 쓰므로, 실데이터로 돌릴 때 이 집계 쿼리가 필요하다.
5. **분석이 리뷰를 읽는 곳** (문제 8).
6. **분석 6번을 개인 기능으로 옮길지** (`docs/proposal-personal-play-style.md`).
7. **환율 출처.** 화면에 원화로 보여 줄 때만 필요 (할인율 분석에는 불필요). `column-mapping.md` 12절 4번과 같은 항목.
8. **⑦ 접속자 적은 온라인 게임 경고(#33)의 "적다" 기준.** 절대값·순위면 지금도 가능하고, "평소보다 적다"면 평소 값이 없어 불가능하다.
9. **콘솔 게임의 구매 타이밍·역대 최저가 표시 방식** (②, #12). 데이터를 쌓는 중이라는 안내와 "수집 이후 최저가" 라벨을 쓸지.

## 컬럼·수집에 요청할 것
수집 파트(`collector/`)를 바꾸는 일이라 요청만 적는다.

| 항목 | 출처 | 필요한 분석 |
|---|---|---|
| **동접자 수집 조기 가동** | `GetNumberOfCurrentPlayers` (키 불필요, 1시간 주기) | 분석 2, 8 / 기능 ⑦ |
| 업데이트·뉴스 날짜 | Steam `ISteamNews/GetNewsForApp` (키 불필요, **새로 시험 필요**: 후보 응답 여부, 과거 범위, 패치 노트 구분, 호출 한도) | 8 |
| **IGDB `release_dates`** (플랫폼·지역별 출시일: `date`, `platform.name`, `region`) | **수집 시험(`check_gaps.py`)에서 이미 요청·수신.** column-mapping 컬럼에 추가만 하면 됨. 지역 코드는 확인 필요(스크립트의 `kr_release`는 region 5, 8을 보는데, 알기로 IGDB는 8=전 세계, 9=한국이라 의도한 지역인지 점검) | 7 |

## 제안
- **바로 진행 가능:** 1·2·4·5번의 로더 구현. 컬럼 이름이 이미 정해져 있다.
- **컬럼 추가 후 진행:** 3·7번 (🔶). `docs/column-additions-request.md`의 평론 점수·플랫폼별 출시일 컬럼이 확정되기 전에는 가능한 범위(7번은 콘솔→PC 이식 지연만)로 계산한다.
- **먼저 할 일:** 동접자 수집 가동(문제 1), 리뷰 상한 값·방식 기록(문제 2), Steam 뉴스 시험(8번).
- **정의가 먼저:** 6번(개인 기능 이동 여부 결정).
- **발표·화면에서의 표현:** 새로 쌓이는 데이터에 기대는 분석(2의 동접 부분, 8)은 "수집 N일치 기반의 초기 결과"로, 실데이터로 확인하지 못한 분석은 "가설"로 소개한다. 콘솔 게임은 "가격 데이터를 쌓는 중이에요"(②), 콘솔 최저가는 "수집 이후 최저가"(#12)로 표시하고, ⑦ 경고는 절대값 기준으로 정의하며, ⑨·⑩은 시연 전에 더미·부하 테스트로 채운다.
